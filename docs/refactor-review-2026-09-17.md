# 模块化重构审查：2026-09-17

审查分支：`codex/modular-refactor`，基线提交 `89d762c`。对照：`origin/main` 的 `c8f49ad`。下文保留初次审查发现，位置行号对应审查基线；后续按用户要求实施的整改及验证见文末。初次审查仅补充文档，两阶段均未更新服务器。

## 结论

本次重构确实建立了功能边界，不是保留旧组件后另加一套实现。原 `components/hub/`、`lib/domain.ts`、`lib/hub-state.ts` 已从 Git 跟踪树删除；文本编辑器、章节组合、命令分发和服务职责均有明确的新入口。

但还不能认为重复和追加覆盖已经全部清除。残留主要是 CSS 长短写与交叠断点、少量公共 HTTP 逻辑、双轨按钮组件以及领域工具归属。架构检查通过只能证明它目前检查的规则，不能证明行为等价或没有语义重复。

## 应优先处理

### 1. 小屏顶部规则在合并后被更宽断点覆盖

位置：`app/features/workspace/shell.css:281–285`、`:367–376`。

`max-width:480px` 中的 `padding-inline:8px`、`gap:4px` 被放到了 `max-width:760px` 前面。后者同样命中手机，且同优先级的 `padding:0 12px`、`gap:6px` 更晚出现，因此最终变成左右 12px、间距 6px。重构前的最终值是左右 8px、间距 4px。

这是已核实的 CSS 结果变化；会减少窄屏标题可用宽度，但未在本次审查中复现实际溢出。建议按从宽到窄的顺序组织断点，或让窄断点规则位于宽断点之后，并保持每个断点内只有一份所属规则。

同类变化：`app/features/notes/styles.css:218–223`，761–800px 下 Note 列表项上下 padding 从重构前最终的 21px 变成 14px。需要明确这是接受的视觉调整，还是恢复重构前结果；不能把它算作完全等价的搬迁。

### 2. 架构检查有可复现的漏检范围

位置：`app/scripts/check-architecture.mjs:47–52`、`:71–104`。

- 服务端路径规则只匹配 `scripts/` 和 `lib/**/server/`，不匹配实际存在的 `lib/account/server.ts`；也没有从客户端入口做传递依赖检查。当前源码扫描未发现客户端已经导入该服务端文件，但规则无法防止未来引入。
- CSS 检查按“媒体条件字符串 + 选择器”识别重复，不检查规则内部的简写/长写重叠，也不计算同时命中的不同媒体条件之间的覆盖。

在隔离临时目录复制原检查器，加入 `features/example/index.ts -> lib/account/server.ts`，以及 `.probe { margin-bottom:31px; margin:0 0 14px; }`；检查仍报告无边界违规、无重复规则。该探针没有写入应用源码。

建议先补充检查器自身的通过/拒绝测试，再增强服务端文件识别、客户端传递依赖检查和 CSS 覆盖审计。不要将一切响应式覆盖视为错误：合法覆盖需要保留，目标是识别被遮蔽的规则和无意的结果变化。

## 不应误删或强行合并的部分

- `components/shared/Modal`、`Picker`、`Segments` 分别使用 `components/ui` 的 Dialog、Select、Tabs：是有调用关系的应用适配，不是重复引擎。
- `features/inbox/pet.tsx` 负责浮动交互和收件状态，`features/pets/frame-player.tsx` 负责画帧，`lib/pets/` 负责素材协议与存储，属于合理分层。
- `lib/repository.ts` 选择账号存储，`lib/storage/repository.ts` 拆合实体，`lib/cloud-repository.ts` 处理远端提交。它们解决不同层次的问题；两处串行队列也保护不同事务边界。
- `storage/payload-v1.ts`、`payload-v2.ts` 是历史传输契约；`core/model.ts` 是当前业务模型。不要为了消除类型相似而删除版本边界。
- MCP 与任务的工作区快照字段限制不同；后者不携带 Note 正文，两者不能直接共用完整序列化输出。
- `summary/engines.ts` 的双方案状态与 provider 协议实现是扩展点。共享覆盖范围、近期窗口计算已集中于 `summary/coverage.ts`，不能把两套独立进度合并。
- `lib/import.ts` 仅重导出解析器，没有第二份解析实现。
- 数据校验函数有“抛错拒绝”与“返回空对象”的不同语义，不能仅凭同名统一。
- 主题 CSS 与 TypeScript 色表有专门的一致性测试，是显式镜像；不应算作未约束的两套主题算法。

## 目录继续收拢的顺序

当前树及日常修改入口见 [架构文档](architecture.md)。建议按实际职责逐步调整，而不是再次全仓移动文件：

1. 先修复上述断点顺序，并给架构检查补充反例测试。
2. 收拢公共 HTTP 机制，消除 MCP/任务与 imports 的非业务耦合；Node HTTP 与 Web Request/Response 仍分开。
3. 明确 shared/ui 的控件关系，清理 CSS 中的失效声明和不再使用的样式。
4. 后续涉及这些文件时，再将 `lib/` 根目录的存储 hooks、备份/回收站、工作区生命周期、附件工具按所属领域归位。比如 React 状态协调器不应与 `core/` 的纯模型混放；但也不必为了文件数少而重新建立总出口。
